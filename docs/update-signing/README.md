# 업데이트 서명 검증 (계획, 미구현)

- 작성일: 2026-10-30
- 상태: 계획만. 구현 전 사용자 결정 필요(§5)
- 관련: `docs/auto-update/README.md` §6 공급망 리스크

## 1. 왜 필요한가
지금 업데이터(`ui/updater.py`)는 exe 와 sha256 을 **둘 다 GitHub 에서** 받는다.
그래서 sha256 은 전송 중 손상만 막는다. GitHub 계정·토큰이 털리면 공격자가 `v9.9.9` 릴리스에
악성 exe 를 올리고, GitHub 가 그 파일로 digest 를 계산해 주므로 검증을 통과한다
→ 하루 안에 모든 친구 PC 에서 실행된다.

이미 적용한 완화책(2FA, Immutable releases)은 **기존 릴리스 변조**만 막고 **새 릴리스 생성**은 못 막는다.

## 2. 방식: Ed25519 공개키 서명
열쇠(서명)를 GitHub 밖, **개발 PC 에만 있는 개인키**로 만든다. GitHub 를 장악해도 개인키가 없으면 서명을 못 만든다.

| 단계 | 내용 |
|---|---|
| 키 생성(1회) | 개인키 → 레포 밖 보관(예: `%USERPROFILE%\.usage_widget_signing\ed25519.key`), 공개키 32바이트 → `ui/updater.py` 상수로 하드코딩 |
| 빌드(`build.bat`) | Defender 검사 뒤 `dist\AIUsageWidget.exe` 의 sha256 을 개인키로 서명 → `dist\AIUsageWidget.exe.sig` |
| 릴리스 | `gh release create vX dist\AIUsageWidget.exe dist\AIUsageWidget.exe.sig ...` |
| 업데이터 | `find_update` 에서 `.sig` asset 도 찾는다. 없으면 설치 안 함. `install` 에서 sha256 확인 후 **공개키로 서명 검증**, 실패 시 `.new` 삭제·설치 안 함 |

서명 대상은 exe 전체가 아니라 sha256 hex 문자열로 한다 (업데이터가 이미 계산하므로 메모리 절약, 구현 단순).

## 3. 구현 선택지
| 안 | 장점 | 단점 |
|---|---|---|
| **A. `cryptography` 번들 (권장)** | 검증된 구현, 코드 몇 줄 | exe 수 MB 증가, 새 의존성 → Defender 오탐 재확인 필요 |
| B. 순수 파이썬 Ed25519 검증 (~60줄) | 의존성 0 | 암호 코드를 손으로 넣는 것 자체가 리스크 |
| C. Authenticode 코드 서명 인증서 | SmartScreen 경고도 사라짐 | 연 수십만 원, 발급 절차 |

## 4. 전환 시 주의
- **v1.0.5 이하 업데이터는 서명을 모른다.** 서명 검증이 들어간 첫 버전(예: v1.0.6)은 지금처럼 sha256 만으로 퍼진다.
  그 이후 버전부터 보호된다. → 첫 버전은 계정 보안이 확실한 상태에서 빨리 내보낼 것.
- **개인키 분실 = 업데이트 영구 불가.** 그 공개키를 가진 exe 는 다른 키의 서명을 거부하므로
  친구들이 exe 를 다시 직접 받아야 한다. → 오프라인 백업(USB 등) 필수.
- **개인키 유출 = 보호 무력화.** 레포·클라우드 동기화 폴더(OneDrive 등)에 두지 말 것. `.gitignore` 로도 막아 둔다.
- 노트북·데스크톱 양쪽에서 빌드한다면 키를 두 머신에 둘지, 한 머신에서만 릴리스할지 정해야 한다.

## 6. 검증 계획 (구현 시)
- `test_providers.py` 에 추가: 올바른 서명 → 설치, 서명 변조 → 거부·`.new` 삭제, `.sig` 없음 → 설치 안 함
- 실제 exe E2E: 구버전 exe 가 서명된 신버전으로 업데이트되는지, 잘못된 키로 서명한 릴리스는 거부하는지
- 빌드 후 Defender 검사 통과 확인
